> この記事は、約2ヶ月の転職活動を一緒に走り抜けた自作 AI エージェントの「作成背景」と「機能・設計」をまとめたものです。
> 最終的に複数社から内定をいただき、1社への入社を決めることができました。その経験で得た知見を、これから転職する人・自分用のエージェントを作りたい人に向けて公開します。
>
> ※ 企業名・個人名・年収などの固有情報はすべて伏せ、仕組みと設計思想に絞って書いています。

## 第1部 なぜ作ったか ── 転職活動の構造的な辛さ

### 転職活動は「並行プロジェクト管理」だった

転職活動を本格的に始めて最初に気づいたのは、これは **同時並行で走る十数個のプロジェクトを、ひとりで管理する仕事** だ、ということでした。

数えてみると、こういう作業がずっと発生し続けます。

- **メールの洪水** ── 応募先・転職エージェント・スカウト媒体から、毎日大量のメールが届く。日程調整の依頼、面接確定の通知、選考結果、求人紹介……どれも見落とすと致命的なのに、重要なものほど他のメールに埋もれる。
- **日程調整** ── 「候補日を3つください」が複数社から同時に来る。カレンダーを見ながら、被らないように、移動時間も考えて返信する。
- **面接準備の分散** ── 企業ごとに事業内容・志望動機・想定質問が違う。準備メモがあちこちのドキュメントに散らばり、「あの会社の何を準備していたか」をすぐ思い出せない。
- **選考状況の俯瞰の喪失** ── 「今どの会社が、どの選考フェーズにいるか」が頭の中だけにある。気づくと「あれ、あの会社って次なんだっけ?」となる。
- **面談の記憶の蒸発** ── 面談で得た手応えや相手の反応は、その日のうちにメモしないと一週間で消える。後から「なぜこの会社に惹かれたんだっけ」が再現できない。

これらは一つひとつは小さい。でも **常時並行で、しかも期限付きで降ってくる** ので、本来エネルギーを注ぐべき「面接そのもの」と「意思決定」に集中できなくなる。転職活動の本質的な辛さは、面接の緊張よりもむしろ **この事務処理の総量と分散** にありました。

### なぜ「チャットボット」ではなく「常駐システム」にしたのか

最初は「ChatGPT に相談すればいいか」と思っていました。でもすぐに限界に気づきます。

チャットは **こちらが話しかけたときしか動かない**。でも転職活動で取りこぼしが起きるのは、まさに「自分が忙しくて画面を開いていない時間」です。メールは自分の都合に関係なく届くし、タスクの期限も勝手に近づいてくる。

そこで方針を変えました。目指したのは、

> **話しかけなくても、裏で勝手に状況を把握し、必要なときだけ通知してくれる「相棒」**

です。具体的には、

- メールは **10分ごとに自分でチェック** して、重要なものをタスク化・下書き作成しておく
- 朝と夜に **その日の新着メールと締切タスクを要約して通知** する
- 面談の録音は **自動で文字起こし・要約され、会社ごとに整理** される
- スマホからでも **チャットアプリ経由で応募状況を確認・相談** できる

つまり「賢いチャット」ではなく、**自分の転職活動を常時バックグラウンドで回す常駐システム** を作ることにしました。土台には [Claude Code](https://www.anthropic.com/claude-code) を選びました。ファイル操作・コマンド実行・外部ツール連携（MCP）が最初から揃っていて、「エージェントの振る舞いを自然言語の設定ファイルで定義できる」点が、まさに作りたかったものに合っていたからです。

## 第2部 どう作ったか ── 機能とアーキテクチャ

### 全体像

```
┌─────────────────────────────────────────────────────┐
│  Claude Code（メインエージェント）                     │
│  ├─ CLAUDE.md         … エージェント定義（参照ハブ）    │
│  ├─ .claude/rules/    … 常時適用の鉄則・規則           │
│  ├─ .claude/skills/   … トリガー発火するワークフロー    │
│  ├─ MCP: job-tracker      … 応募・タスク管理           │
│  └─ MCP: google-calendar  … カレンダー操作            │
└──────────┬──────────────────────────────┬────────────┘
           │                              │
    ┌──────▼──────┐               ┌───────▼───────┐
    │ Discord Bot │               │ Gmail Daemon  │
    │（どこからでも │◄──────────────│ 10分ごとに監視  │
    │   会話する）  │   通知         │ 分類→タスク→下書き│
    └─────────────┘               └───────────────┘
           │                              │
           ▼                              ▼
    ┌─────────────────────────────────────────────┐
    │  data/applications/*.md  （応募の構造化データ）  │
    │  knowledge/              （経歴・企業研究・人脈） │
    │  memory/                 （面談の洞察・気づき）   │
    └─────────────────────────────────────────────┘
                       ▲
               ┌───────┴────────┐
               │  面談録音の同期  │
               │  → 自動文字起こし │
               │  → 要約・会社別配置│
               └────────────────┘
```

ポイントは、**Claude Code 本体を「頭脳」、複数の常駐プロセスを「手足」** として分離したことです。頭脳は対話と判断を担当し、手足はメール監視・通知・文字起こしといった「自分が見ていない時間に動くべき仕事」を担当します。

### 技術スタック

| 領域 | 採用したもの |
|---|---|
| ランタイム | Bun |
| 言語 | TypeScript |
| AI | Claude Code / Claude API（対話・メール分類・下書き生成すべて Claude 経由） |
| エージェント間連携 | MCP（Model Context Protocol） |
| データ | Markdown + YAML frontmatter（**DB を使わない**ファイルベース） |
| 外部API | Gmail API / Google Calendar API / Discord |
| 常駐・定時実行 | macOS launchd |

### 機能 1：チャットアプリからどこでも話せる「相棒」（すべての出発点）

実は、このシステムで一番最初に作ったのがこの機能です。**「PCの前に座っていなくても、スマホからいつでも相談できる相棒が欲しい」** ── そこがすべての出発点でした。

チャットアプリ（Discord）にメッセージを送ると、それがそのまま Claude Code への入力になり、応答が返ってくるボットを立てています。

- メッセージを受け取ると Claude CLI をサブプロセスとして起動
- **会話セッションIDを保存して文脈を継続**（24時間操作がなければ自動リセット）
- 長い応答はチャットの文字数上限に合わせて自動分割

これで「PCの前のターミナル」に縛られず、**通勤中にスマホから『今日空いてる時間は?』『○○社って今どの選考だっけ?』と聞く** ような使い方ができるようになりました。

そして、この「どこからでも話せる入口」を手に入れたことで欲が出ます。**『どうせなら、話しかけなくても裏で勝手に動いてほしい』** ── そこから先に紹介する常駐機能（応募管理・メール監視・定期通知・自動要約）へと広げていった、というのが実際の作られ方です。まずは入口を作り、そこに手足を生やしていった、という順番でした。

### 機能 2：応募管理を専用 MCP サーバーで

転職活動の中核データ ──「どの会社の、どのポジションに、いつ応募して、今どのフェーズか」── は、自作の MCP サーバー `job-tracker` で管理しています。Claude から次のようなツールを呼べます。

| ツール | 役割 |
|---|---|
| `create_application` | 応募企業を登録 |
| `update_application_status` | 選考ステータスを更新 |
| `list_applications` | 応募一覧（ステータスでフィルタ可） |
| `create_task` | タスクを作成（面接準備・書類提出など） |
| `complete_task` | タスクを完了にする |
| `get_overdue_tasks` | 期限超過・滞留タスクを取得 |

ステータスは選考フェーズに沿って、決まった順序でしか遷移しないようにしています。

```
applied → screening → interview → offer → accepted
                                        ↘ rejected
```

「○○社に応募した」と話しかければ自動で登録され、「応募状況を見せて」で一覧が出て、「○○社が一次面接に進んだ」でステータスが更新される ── という体験です。

### 機能 3：データは「Markdown + frontmatter」、DB を使わない

応募1社につき1ファイル。中身はこういう構造です（内容はダミー）。

```markdown
---
id: example-001
company_name: Example株式会社
position: プロダクトマネージャー
status: interview
applied_at: 2026-01-15
updated_at: 2026-01-20
email_domain: example.co.jp
---

## メモ
企業研究・志望動機など

## タスク
- [x] 書類提出 `id:t001` `priority:high` `completed:2026-01-16`
- [ ] 面接準備 `id:t002` `priority:high` `due:2026-01-25`
```

DB ではなく **あえて Markdown ファイル** にしたのは後述の設計判断に効いてきます。要点だけ言うと、人間も Claude も同じファイルを直接読めて、特別な DB クライアントや閲覧ツールが要らないからです。

### 機能 4：Gmail を10分ごとに監視するデーモン

転職活動の「取りこぼし」が一番起きるメールには、専用の常駐デーモンを当てました。10分間隔で新着メールをポーリングし、1通ずつ次の処理をします。

1. **会社の特定** ── 送信ドメイン・本文から、どの応募先 or どのエージェントからのメールかを判定
2. **分類** ── Claude API でメールの種別を判定（日程調整依頼 / 面接確定 / 書類結果 / 内定 / 不採用 / エージェント連絡 / カジュアル面談確定 / その他）と緊急度を付与
3. **通知** ── 重要なものをデスクトップ通知
4. **タスク自動生成** ── 種別に応じたタスクを、緊急度から逆算した期限つきで該当応募ファイルに追記
5. **返信下書きの自動作成** ── 日程調整依頼・面談確定・選考結果には、自分の経歴プロフィールを踏まえた返信下書きを Gmail に作成し、チャットに「下書きできました」と通知

分類はこんなプロンプトで、構造化された JSON を返させています（抜粋）。

```
emailType の判断基準:
- schedule_request : 日程調整の依頼（返信が必要なもの）
- interview_schedule: 面接日程の確定通知
- document_result  : 書類選考の結果通知
- offer            : 内定・オファーレター
- rejection        : 不採用通知
- agent_contact    : エージェントからの求人紹介・一般連絡
- casual_meeting   : カジュアル面談の確定通知
- other            : その他
```

緊急度はタスクの締切に直結します。`high` なら翌日、`medium` なら3日後、`low` なら1週間後を期限に設定。「重要なメールほど早い締切のタスクになる」よう自動化しました。

> ちなみにこのデーモンには、**失敗したメールの処理時刻まで「最終チェック時刻」を巻き戻して次回再処理する** リトライ機構や、**多重起動を防ぐ PID ロック** も入れています。常駐させる以上、止まっても・重複しても壊れないことが重要でした。

### 機能 5：朝と夜の定期ブリーフィング

毎朝6:30と毎晩20:30に、定時ジョブが走ってチャットに要約を投げます。

- **新着メール** ── 応募先・エージェントから直近に届いたメールの一覧
- **期限超過タスク** ── 締切を過ぎた未対応タスク
- **今日のタスク** ── 今日が締切のタスク

「自分から確認しに行かなくても、1日2回、状況のほうから報告に来る」状態を作りました。これがあるだけで「何か見落としているのでは」という地味な不安がかなり消えます。

### 機能 6：面談の録音を自動で要約・整理するパイプライン

面談・面接は録音して文字起こしツールにかけ、テキストをクラウドストレージに自動エクスポートしています。そこから先を、5分間隔の同期スクリプトが自動でやります。

1. クラウドから新しい文字起こしファイルを同期
2. Claude に渡し、**カレンダーの予定・応募データ・本文を突き合わせて「どの会社の面談か」を特定**
3. 構造化サマリを生成 ──「面談の要点」「相手のポジティブ/ネガティブシグナル」「総合判断」「次のアクション」
4. 会社ごとのフォルダに自動配置
5. さらに応募ステータスと面接対策メモ（`meeting-prep.md`）を自動更新

ここで効いた工夫が **「エージェント面談」の扱い** です。転職エージェントとの面談では複数の応募先企業の話が出ます。そのまま分類すると「話題に出ただけの会社」のフォルダに保存されてしまう。そこで「エージェント面談はエージェント自身のフォルダに保存し、応募先の選考更新はしない」という判定ルールを明示的に入れました。**自動化は、こうした例外を言語化できるかどうかで品質が決まる** と実感した部分です。

### 機能 7：知識ベースとしての `knowledge/` と `memory/`

応募の「構造化データ」が `data/applications/` だとすると、人間が読む文章ベースの知識は `knowledge/` に置いています。

```
knowledge/
├── profile.md           # 経歴・スキル・強み
├── resume.md            # 詳細な職務経歴
├── values.md            # 転職軸・条件・給与希望
├── status-overview.md   # 全社の選考ステータス俯瞰
├── companies/{slug}/    # 会社ごとの企業研究・志望動機・面接対策
└── networking/          # 個人との面談・会食の記録
```

志望動機書や面接対策を生成するときは、この `profile.md`・`values.md` と企業フォルダを参照して、**自分の経歴と企業を踏まえた内容** を作らせます。新しい応募先は、サブエージェント（後述）が Web 検索で企業プロフィールの草案まで作ってくれます。

## 第3部 設計で効いた判断

ここが、自分用エージェントを作りたい人に一番伝えたい部分です。2ヶ月運用してみて「これは効いた」と思える設計判断が4つあります。

### 判断1：状態を「DB」ではなく「Markdownファイル」に置いた

応募データもタスクも、すべて Markdown + YAML frontmatter のファイルです。最初は「ちゃんと DB にすべきでは」と思いましたが、ファイルベースにしたことで次の利点が全部ついてきました。

- **Claude が状態を直接読み書きできる** ── DB クライアントを介さず、ファイルを読むだけで全状況を把握できる。エージェントとデータの相性が最高に良い。
- **人間もそのまま読める** ── 専用の管理画面が要らない。エディタで開けば全部わかる。
- **プレーンテキストで取り回しが軽い** ── grep で検索でき、どのエディタでも開け、バックアップもコピーひとつで済む。
- **常駐デーモンも同じファイルを読める** ── メールデーモンも定時ジョブも、同じ Markdown を読んでドメイン一覧やタスクを集計する。**共通の真実が1箇所にある**。

「AI エージェントの状態管理は、まず human-readable なファイルから始める」のは、個人用ツールではかなり筋が良い選択だと感じました。

### 判断2：振る舞いを「ハーネス」で設計した

LLM 単体は、放っておけば毎回ちがう動き方をする「賢いけれど気まぐれな部品」です。これを転職支援エージェントとして安定して働かせるには、**モデルを取り囲んで振る舞いを方向づける足場 ── いわゆる「ハーネス」** をどう設計するかが肝になります。

ありがちな失敗は、このハーネスを「巨大な1枚のプロンプト」として書いてしまうことです。手順も禁止事項も口調も全部 `CLAUDE.md` に詰め込むと、すぐに読みづらく・壊れやすくなる。そこで **ハーネスを役割ごとのファイルに分解** し、`CLAUDE.md` 本体は各ファイルを指す **薄い「参照ハブ」** に保ちました。

```
.claude/
├── rules/    … 常時適用される鉄則・規則（口調・命名・データ同期）
├── skills/   … 特定の状況で発火するワークフロー
└── agents/   … 重い調査を委譲するサブエージェント
```

このハーネスで特に効いたのが **`skills/`（トリガー発火するワークフロー）** という層です。「常に全手順を読ませる」のではなく「この状況になったらこの手順だけを引き込む」ようにしました。たとえば、

- 「○○社に応募した」→ `new-application` スキルが発火し、登録・ファイル作成・企業研究を一気通貫で実行
- 選考ステータスが変わった → `status-overview-sync` スキルが発火し、**構造化データと俯瞰ビューの両方を必ず同時更新**（片方だけ更新して不整合になるのを防ぐ）
- 「下書き作って」→ `email-draft` スキルが発火し、後述の鉄則に沿った下書きだけを生成

つまり、モデルの賢さに丸投げするのではなく、**「いつ・何を・どの手順で」をハーネス側で構造化して与える**。これでメインの定義は読みやすく保たれ、状況ごとの振る舞いが安定しました。次の「判断3」で触れる鉄則も、このハーネスの中で最優先に置かれる安全装置の層です。

### 判断3：絶対にやってはいけないことを「鉄則」として明文化した

メールの誤送信や面談での失言は、転職活動では取り返しがつきません。そこで **「すべての操作に優先する不変ルール」** を `ironclad.md` という1ファイルに集約しました。たとえば、

- **メール下書きは本文のみ**。件名・ラベル・AIへの指示文・内部メモを絶対に混入させない
- **返信は必ず全員返信（Reply-All）**。To / CC を取りこぼさない
- **スケジュールの正はカレンダーのみ**。記憶や推測で日程を答えず、必ずカレンダー API を叩く
- **面談で言ってはいけないこと** を明示

AI に自由に動いてもらいつつ、**「これだけは絶対にしない」を1箇所で強制する** 設計。エージェントを「賢くする」より「事故らせない」ほうが、実運用ではずっと重要でした。

### 判断4：「やったこと」と「学んだこと」を分けて記録した

記録を2種類に分けたのも効きました。

| | 記録するもの | 寿命 |
|---|---|---|
| **セッションログ** | 何を **やったか**（行動の記録） | セッション単位で上書き |
| **memory/** | 何を **学んだか**（洞察・気づき・転職軸の変化） | 永続的に蓄積 |

面談後の「この会社、技術面接が心地よかった」「やっぱり自分はこの条件を重視している」といった **主観的な気づき** は `memory/` に永続化し、次の面接準備や意思決定で参照します。**事実は `knowledge/` に、洞察は `memory/` に、行動履歴はセッションログに** ── 情報の性質ごとに置き場所を分けたことで、後から「なぜそう判断したか」を再現できるようになりました。

## 第4部 何が変わったか・再現方法

### 何が変わったか

定量化はできませんが、体感で一番大きかったのは **「認知の負荷が下がった」** ことです。

- メールの取りこぼし不安が消えた（10分ごとに見て、タスク化・下書きまでしてある）
- 「今どういう状況か」をいつでも一覧で確認できる（頭の中で覚えなくてよい）
- 面談の振り返りが資産として積み上がる（手応えが消えない）
- 事務処理が裏で回るので、**面接と意思決定という本質に集中できた**

結果として、複数社から内定をいただき、納得して1社を選ぶところまで走り切れました。エージェントが内定を取ってくれたわけではありません。でも、**「自分が本当に向き合うべきこと」に時間とエネルギーを残してくれた** ことが、結果に効いたと思っています。

### 自分用に再現するなら

フルセットはやや重いので、効果の大きい順におすすめします。

1. **応募管理を1つのファイル群にする** ── まずは Markdown + frontmatter で「全応募の状態が1箇所でわかる」状態を作る。ここだけでも頭がかなり軽くなる。
2. **絶対NG を明文化する** ── メール・発言・スケジュールの「やってはいけない」を1ファイルに書き、AI に常時読ませる。事故防止の費用対効果が最も高い。
3. **状況別のワークフローを外出しする** ── 「この状況ならこの手順」をスキルとして分離する。
4. **メール監視を常駐させる** ── ここまで来ると「裏で動く相棒」になる。リトライと多重起動防止だけは丁寧に。
5. **面談の文字起こしを自動要約する** ── 振り返りが資産になる。

### 注意点：個人情報の扱い

このシステムは経歴・年収・企業とのやり取りという **極めてセンシティブな情報** を扱います。設計上は、

- 公開してよいもの（応募管理 MCP のような汎用ロジック）と、ローカルに留めるべきもの（経歴・応募データ・メール下書き）を **`.gitignore` で明確に分離**
- 個人データのディレクトリはリポジトリに含めない

としています。ただし `.gitignore` を壊したり強制追加すれば情報は漏れます。**自分専用ツールであっても、機密情報の置き場所と公開境界は最初に設計しておくべき** です。

## 第5部 もし「課金後」だったら ── 2026年6月15日の料金改定で試算

> ここはお金の話です。同じものを作ろうとする人には一番リアルに効いてくる章であり、正直、書いていて一番ゾッとした章でもあります。

### 2026年6月15日に何が変わったか

2026年6月15日から、Anthropic は **プログラム経由（ヘッドレス）の Claude 利用を、対話利用とは別枠の従量クレジットに分離** しました。要点だけ整理すると、

- **対象**：`claude -p`（ヘッドレス／プリントモード）・Claude Agent SDK・GitHub Actions など、**スクリプトや cron から自動で叩く実行**
- **非対象**：ターミナルや IDE で人間が対話する通常の `claude`
- 自動実行ぶんには、サブスクとは別に **毎月の専用クレジット（Pro $20 / Max 5x $100 / Max 20x $200 相当）** が割り当てられ、それを **標準 API レートで消費**。超えた分は従量課金

ひとことで言えば、**「定額サブスクで自動化を回し放題」が終わり、自動化＝API レート課金になった** ということです。

### なぜこのシステムが"直撃"なのか

このシステムは、**自動化部分がほぼ全部 `claude -p`** で動いています（メール分類・面談要約・Discord 応答・定期通知）。人間が相談する対話部分は対象外ですが、**裏で回り続ける自動化は丸ごと新クレジットの対象** です。

そして、ここが正直に書いておくべきところなのですが ── **ヘッドレスで安いモデルを少し叩くだけ、月にせいぜい数十ドルだろう**、と計測するまで思い込んでいました。実測は、桁が違いました。

### 実測：記録の残る1ヶ月で約 $990、転職活動全体で約 $2,500

使用実績をモデル別に集計したところ、**記録の残っている直近1ヶ月（2026年5月6日〜6月5日）だけで、合計 $990.51（¥156,501）／2,575メッセージ** を消費していました。「月にせいぜい数十ドル」という当初の見込みは、文字どおり桁違いでした。

| モデル | メッセージ数 | 出力トークン | キャッシュ読込 | コスト (USD) | コスト (¥) |
|---|---:|---:|---:|---:|---:|
| **Opus 4.6** | 1,453 | 768K | 106M | **$852.75** | ¥134,734 |
| Sonnet 4.6 | 462 | 619K | 16M | $39.79 | ¥6,286 |
| Haiku 4.5 | 494 | 349K | 19M | $18.32 | ¥2,894 |
| Opus 4.7 / 4.8（試運転・当日分） | 166 | 316K | 13M | $79.66 | ¥12,585 |
| **合計** | **2,575** | **2.05M** | **154M** | **$990.51** | **¥156,501** |

この表が物語っていることが、ふたつあります。

1. **コストの約86%が Opus 4.6 に集中**（$852.75 / $990.51）。判断品質を優先して高価なモデルを当てていた部分が、そのまま費用の大半でした。
2. **キャッシュ読込が1ヶ月で 1.5億トークン超（154M）**。これは、エージェントが毎ターン CLAUDE.md・ルール・会話履歴・面談の書き起こしといった **大きなコンテキストを読み直し続けた** 結果です。まさに *コンテキスト課金* そのもの。コストの主役が「長いコンテキスト × 何度も往復するエージェント的な処理」だったことが、数字に表れています。

:::message
なお、これは **記録が残っている1ヶ月ぶん** です。実は5月6日より前、約1ヶ月半は MacBook Air で運用していて、**ゴールデンウィークに Mac mini を購入して入れ替えた際に、それ以前の正確なログが残りませんでした**。使い方はその間ほとんど変えていないので、単純計算で **転職活動全体ではこの約2.5倍 ── ざっくり $2,500（¥39万前後）** を、このエージェント1つに費やしていた計算になります。
:::

### 6/15以降だったら、いくら払っていたか

この使用量のうち、裏で回り続ける自動化（`claude -p`）のぶんが、**6/15以降は月次クレジットを超えた分を API レートで請求される** 対象になります。記録の残る **月およそ $990** に対して、サブスクに含まれる月次クレジットがどれだけ賄えるかを見ると、こうなります。

| プラン | 月次クレジット | $990 に対する充当率 |
|---|---:|---:|
| Pro | $20 | 約 2% |
| Max 5x | $100 | 約 10% |
| Max 20x | $200 | 約 20% |

**最上位プランのクレジットでも、賄えるのは2割ほど**。残りは API レートの従量課金です。記録に残らない期間も含めた転職活動全体では、**自動実行が占めるぶんに応じて、最大で $2,000〜2,500（30〜39万円）規模** が実費としてのしかかっていた計算になります。

:::message
厳密には、自分でターミナルから対話していたぶんは6/15以降も従来どおりサブスク枠で、**実際に従量化されるのは「自動実行が占める割合」ぶん** です。とはいえ、この規模では月数百ドル単位の実費は避けられません。
:::

裏を返せば、**6/15までは、これだけの計算資源を定額サブスクの内側で回せていた** ということでもあります。今回の改定は「使い放題の終わり」であると同時に、自分がどれだけの処理を AI に肩代わりさせていたかを、金額で突きつけてくる出来事でもありました。

### じゃあ、6/15以降に同じものを作るなら

この実測から、課金後に現実的に運用するための処方箋もはっきりしました。

1. **モデルを用途で振り分ける** ── 高頻度・定型は Haiku、本当に判断力が要る所だけ Sonnet/Opus。実際このあと、面談要約は Opus → Sonnet に落としました（体感の品質はほぼ維持できています）。
2. **「長コンテキスト × ツール往復」を真っ先に疑う** ── コストの主役はここ。書き起こしを全文渡すのをやめて要点抽出を挟む、ツール呼び出し回数を絞る、プロンプトキャッシュやバッチ API を使う ── といった最適化が一番効きます。
3. **使い捨ての呼び出しは最小コンテキストで** ── `/tmp` から叩いて、余計な設定やルールを毎回ロードさせない。塵も積もれば、です。
4. **ハーネス／ベンダーを1つに固定しない** ── 自動化が従量課金になった以上、「Claude Code 一択」である必然性はもうありません。作り直すなら、**OpenAI の [Codex](https://github.com/openai/codex)**（GPT-5.5 ベースの対抗馬。`npm` で入る CLI で、コスパもベンチも拮抗）や、**[Hermes Agent](https://github.com/nousresearch/hermes-agent)**（Nous Research のオープンソース・エージェント）も試したいところです。とくに Hermes Agent は **自前インフラ＋好きな LLM で動かせる**ので従量課金そのものを避けやすく、さらに **永続メモリ・経験から育つスキル・メッセージング基盤** を標準装備しています。これはまさに、本システムが手作りした `memory/`・`skills/`・Discord の入口に相当する仕組みで、乗り換え先としての相性が良さそうです。

:::message alert
ここに挙げた金額はすべて実測ベースですが、月によって変動します。**自分で作る人は、必ず `/cost` や [Anthropic コンソール](https://console.anthropic.com) で自分の実消費を確認してください。** 私のように、概算と実測が20〜30倍ずれていることがあります。「計測するまでコストはわからない」── これが、この章の一番の学びでした。
:::

## おわりに

転職活動を「ひとりで捌く並行プロジェクト管理」と捉え直し、その事務処理を AI エージェントに常駐で肩代わりさせた ── というのが、このシステムの全体像です。

派手な「AI が転職を自動化する」話ではありません。むしろ逆で、**面接や意思決定という"人間が向き合うべき部分"に集中できるよう、それ以外を徹底的に裏方に回した** 結果でした。

同じように転職活動の事務処理に消耗している人、あるいは自分用の常駐エージェントを作ってみたい人にとって、この設計が何かのヒントになれば嬉しいです。
