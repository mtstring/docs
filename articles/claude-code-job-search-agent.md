> この記事は、数ヶ月にわたる転職活動を一緒に走り抜けた自作 AI エージェントの「作成背景」と「機能・設計」をまとめたものです。
> 最終的に納得のいく形で転職先を決められました。そこで得た知見を、これから転職する人・自分用のエージェントを作りたい人に向けて公開します。
>
> ※ 企業名・個人名・年収などの固有情報はすべて伏せ、仕組みと設計思想に絞って書いています。

## 第1部 なぜ作ったか ── 転職活動の構造的な辛さ

### 転職活動は「並行プロジェクト管理」だった

転職活動を始めてすぐ気づいたのは、これが **同時並行で走る十数個のプロジェクトを、ひとりで管理する仕事** だということです。

具体的には、こういう作業が常時発生し続けます。

- **メールの洪水** ── 応募先・転職エージェント・スカウト媒体から、毎日大量のメールが届く。日程調整の依頼、面接確定の通知、選考結果、求人紹介……どれも見落とすと致命的なのに、重要なものほど他のメールに埋もれる。
- **日程調整** ── 「候補日を3つください」が複数社から同時に来る。カレンダーを見ながら、被らないように、移動時間も考えて返信する。
- **面接準備の分散** ── 企業ごとに事業内容・志望動機・想定質問が違う。準備メモがあちこちのドキュメントに散らばり、「あの会社の何を準備していたか」をすぐ思い出せない。
- **選考状況の俯瞰の喪失** ── 「今どの会社が、どの選考フェーズにいるか」が頭の中だけにある。気づくと「あれ、あの会社って次なんだっけ?」となる。
- **面談の記憶の蒸発** ── 面談で得た手応えや相手の反応は、その日のうちにメモしないと一週間で消える。後から「なぜこの会社に惹かれたんだっけ」が再現できない。

一つひとつは小さい作業です。しかし **常時並行で、期限付きで降ってくる** ため、本来注力すべき「面接」と「意思決定」に集中できなくなる。転職活動の本質的な辛さは **事務処理の総量と分散** にありました。

### 作りたかったのは「自分専用のAI転職エージェント」

起点は **「転職をサポートしてくれる自分専用のエージェント（秘書）を、AI で作ってみたい」** でした。状況を把握し、相談に乗り、細かい事務も引き受ける ── 人間の転職エージェントの仕事を、自分専用に持つイメージです。

前提としてひとつ決めていたのは **「PC を開かなくても使えること」**。相談や確認は、通勤中・外出先・面接直前といった「PC の前にいない時間」にこそ発生します。スマートフォンだけで相談・連絡・スケジュール確認が完結する **手軽さ** を最優先しました。

最初から完成形を設計したわけではなく、使いながら **「これもやってほしい」が出るたびに機能を継ぎ足していきました**。

- 日程調整に追われ、**スケジュール管理（カレンダー連携）** を追加
- メールの洪水に埋もれ、**重要なメールだけ拾って教えてくれる監視**（10分ごとにチェックし、タスク化・下書きまで）を追加
- 面談の記憶が蒸発するので、**録音の自動文字起こし・要約・会社ごとの整理** を追加
- 面接前の準備のために、**企業情報を事前にリサーチして教えてくれる機能** を追加
- 朝と夜には **新着メールと締切タスクの要約通知** を追加

気づけば、単なる「賢いチャット」ではなく **自分の転職活動を常時バックグラウンドで回す常駐システム** に育っていました。土台は [Claude Code](https://www.anthropic.com/claude-code) です。ファイル操作・コマンド実行・外部ツール連携（MCP）が最初から揃っていて、「エージェントの振る舞いを自然言語の設定ファイルで定義できる」点が作りたいものに合っていました。

## 第2部 どう作ったか ── 機能とアーキテクチャ

### 全体像

```
┌─────────────────────────────────────────────────────┐
│  Claude Code（メインエージェント）                     │
│  ├─ CLAUDE.md         … エージェント定義（参照ハブ）    │
│  ├─ .claude/rules/    … 常時適用の鉄則・規則           │
│  ├─ .claude/skills/   … トリガー発火するワークフロー    │
│  ├─ MCP: job-tracker      … 応募・タスク管理           │
│  └─ MCP: google-calendar  … カレンダー操作            │
└──────────┬──────────────────────────────┬────────────┘
           │                              │
    ┌──────▼──────┐               ┌───────▼───────┐
    │ Discord Bot │               │ Gmail Daemon  │
    │（どこからでも │◄──────────────│ 10分ごとに監視  │
    │   会話する）  │   通知         │ 分類→タスク→下書き│
    └─────────────┘               └───────────────┘
           │                              │
           ▼                              ▼
    ┌─────────────────────────────────────────────┐
    │  data/applications/*.md  （応募の構造化データ）  │
    │  knowledge/              （経歴・企業研究・人脈） │
    │  memory/                 （面談の洞察・気づき）   │
    └─────────────────────────────────────────────┘
                       ▲
               ┌───────┴────────┐
               │  面談録音の同期  │
               │  → 自動文字起こし │
               │  → 要約・会社別配置│
               └────────────────┘
```

ポイントは、**Claude Code 本体を「頭脳」、複数の常駐プロセスを「手足」** として分離したことです。頭脳は対話と判断を担当し、手足はメール監視・通知・文字起こしといった「自分が見ていない時間に動くべき仕事」を担当します。

### 技術スタック

| 領域 | 採用したもの |
|---|---|
| ランタイム | Bun |
| 言語 | TypeScript |
| AI | Claude Code / Claude API（対話・メール分類・下書き生成すべて Claude 経由） |
| エージェント間連携 | MCP（Model Context Protocol） |
| データ | Markdown + YAML frontmatter（**DB を使わない**ファイルベース） |
| 外部API | Gmail API / Google Calendar API / Discord |
| 常駐・定時実行 | macOS launchd |

### 機能 1：チャットアプリからどこでも話せる「相棒」（すべての出発点）

このシステムで最初に作った機能です。**「PC の前に座っていなくても、スマホからいつでも相談できる相棒が欲しい」** ── そこが出発点でした。

チャットアプリ（Discord）にメッセージを送ると、それがそのまま Claude Code への入力になり、応答が返ってくるボットを立てています。

- メッセージを受け取ると Claude CLI をサブプロセスとして起動
- **会話セッションIDを保存して文脈を継続**（24時間操作がなければ自動リセット）
- 長い応答はチャットの文字数上限に合わせて自動分割

これでターミナルに縛られず、**通勤中にスマホから「今日空いてる時間は?」「○○社って今どの選考だっけ?」と聞ける** ようになりました。

この入口ができると、**「どうせなら、話しかけなくても裏で勝手に動いてほしい」** という欲が出ます。そこから常駐機能（応募管理・メール監視・定期通知・自動要約）へ広げていきました。まず入口を作り、あとから手足を生やしていった順番です。

### 機能 2：応募管理を専用 MCP サーバーで

転職活動の中核データ ──「どの会社の、どのポジションに、いつ応募して、今どのフェーズか」── は、自作の MCP サーバー `job-tracker` で管理しています。Claude から次のようなツールを呼べます。

| ツール | 役割 |
|---|---|
| `create_application` | 応募企業を登録 |
| `update_application_status` | 選考ステータスを更新 |
| `list_applications` | 応募一覧（ステータスでフィルタ可） |
| `create_task` | タスクを作成（面接準備・書類提出など） |
| `complete_task` | タスクを完了にする |
| `get_overdue_tasks` | 期限超過・滞留タスクを取得 |

ステータスは選考フェーズに沿って、決まった順序でしか遷移しないようにしています。

```
applied → screening → interview → offer → accepted
                                        ↘ rejected
```

「○○社に応募した」と話しかければ自動で登録され、「応募状況を見せて」で一覧が出て、「○○社が一次面接に進んだ」でステータスが更新される ── という体験です。

### 機能 3：データは「Markdown + frontmatter」、DB を使わない

応募1社につき1ファイル。中身はこういう構造です（内容はダミー）。

```markdown
---
id: example-001
company_name: Example株式会社
position: プロダクトマネージャー
status: interview
applied_at: 2026-01-15
updated_at: 2026-01-20
email_domain: example.co.jp
---

## メモ
企業研究・志望動機など

## タスク
- [x] 書類提出 `id:t001` `priority:high` `completed:2026-01-16`
- [ ] 面接準備 `id:t002` `priority:high` `due:2026-01-25`
```

DB ではなく **あえて Markdown ファイル** にしたのは、人間も Claude も ── そして後述の常駐デーモンも ── 同じファイルを直接読めて、特別な DB クライアントや閲覧ツールが要らないからです。grep で検索でき、バックアップもコピーひとつで済み、**共通の真実が1箇所にある** 状態を保てます。

### 機能 4：Gmail を10分ごとに監視するデーモン

転職活動の「取りこぼし」が一番起きるメールには、専用の常駐デーモンを当てました。10分間隔で新着メールをポーリングし、1通ずつ次の処理をします。

1. **会社の特定** ── 送信ドメイン・本文から、どの応募先 or どのエージェントからのメールかを判定
2. **分類** ── Claude API でメールの種別を判定（日程調整依頼 / 面接確定 / 書類結果 / 内定 / 不採用 / エージェント連絡 / カジュアル面談確定 / その他）と緊急度を付与
3. **通知** ── 重要なものをデスクトップ通知
4. **タスク自動生成** ── 種別に応じたタスクを、緊急度から逆算した期限つきで該当応募ファイルに追記
5. **返信下書きの自動作成** ── 日程調整依頼・面談確定・選考結果には、自分の経歴プロフィールを踏まえた返信下書きを Gmail に作成し、チャットに「下書きできました」と通知

分類はこんなプロンプトで、構造化された JSON を返させています（抜粋）。

```
emailType の判断基準:
- schedule_request : 日程調整の依頼（返信が必要なもの）
- interview_schedule: 面接日程の確定通知
- document_result  : 書類選考の結果通知
- offer            : 内定・オファーレター
- rejection        : 不採用通知
- agent_contact    : エージェントからの求人紹介・一般連絡
- casual_meeting   : カジュアル面談の確定通知
- other            : その他
```

緊急度はタスクの締切に直結します。`high` なら翌日、`medium` なら3日後、`low` なら1週間後を期限に設定。「重要なメールほど早い締切のタスクになる」よう自動化しました。

> このデーモンには、**失敗したメールの処理時刻まで「最終チェック時刻」を巻き戻して次回再処理する** リトライ機構と、**多重起動を防ぐ PID ロック** も入れています。常駐させる以上、止まっても・重複しても壊れないことが重要です。

### 機能 5：朝と夜の定期ブリーフィング

毎朝6:30と毎晩20:30に、定時ジョブが走ってチャットに要約を投げます。

- **新着メール** ── 応募先・エージェントから直近に届いたメールの一覧
- **期限超過タスク** ── 締切を過ぎた未対応タスク
- **今日のタスク** ── 今日が締切のタスク

「自分から確認しに行かなくても、1日2回、状況のほうから報告に来る」状態です。「何か見落としているのでは」という不安はこれでほぼ消えました。

### 機能 6：面談の録音を自動で要約・整理するパイプライン

面談・面接は録音して文字起こしツールにかけ、テキストをクラウドストレージに自動エクスポートしています。そこから先を、5分間隔の同期スクリプトが自動でやります。

1. クラウドから新しい文字起こしファイルを同期
2. Claude に渡し、**カレンダーの予定・応募データ・本文を突き合わせて「どの会社の面談か」を特定**
3. 構造化サマリを生成 ──「面談の要点」「相手のポジティブ/ネガティブシグナル」「総合判断」「次のアクション」
4. 会社ごとのフォルダに自動配置
5. さらに応募ステータスと面接対策メモ（`meeting-prep.md`）を自動更新

効いた工夫が **「エージェント面談」の扱い** です。転職エージェントとの面談では複数の応募先企業の話が出るため、そのまま分類すると「話題に出ただけの会社」のフォルダに保存されてしまう。そこで「エージェント面談はエージェント自身のフォルダに保存し、応募先の選考更新はしない」という判定ルールを明示しました。**自動化の品質は、こうした例外を言語化できるかで決まります**。

### 機能 7：知識ベースとしての `knowledge/` と `memory/`

応募の「構造化データ」が `data/applications/` だとすると、人間が読む文章ベースの知識は `knowledge/` に置いています。

```
knowledge/
├── profile.md           # 経歴・スキル・強み
├── resume.md            # 詳細な職務経歴
├── values.md            # 転職軸・条件・給与希望
├── status-overview.md   # 全社の選考ステータス俯瞰
├── companies/{slug}/    # 会社ごとの企業研究・志望動機・面接対策
└── networking/          # 個人との面談・会食の記録
```

志望動機書や面接対策を生成するときは、この `profile.md`・`values.md` と企業フォルダを参照して、**自分の経歴と企業を踏まえた内容** を作らせます。新しい応募先は、サブエージェント（後述）が Web 検索で企業プロフィールの草案まで作ってくれます。

### 機能 8：すべてを支える「ハーネス」設計

ここまでの機能すべてを支えている設計の話です。LLM 単体は、毎回ちがう動き方をしうる「賢いが気まぐれな部品」です。安定して働かせるには、**モデルを取り囲んで振る舞いを方向づける足場 ── いわゆる「ハーネス」** の設計が肝になります。

ありがちな失敗は、このハーネスを「巨大な1枚のプロンプト」として書いてしまうことです。手順も禁止事項も口調も全部 `CLAUDE.md` に詰め込むと、すぐに読みづらく・壊れやすくなる。そこで **ハーネスを役割ごとのファイルに分解** し、`CLAUDE.md` 本体は各ファイルを指す **薄い「参照ハブ」** に保ちました。

```
.claude/
├── rules/    … 常時適用される鉄則・規則（口調・命名・データ同期）
├── skills/   … 特定の状況で発火するワークフロー
└── agents/   … 重い調査を委譲するサブエージェント
```

`rules/` の核は **「絶対にやってはいけないこと」の明文化** です。「メール下書きは本文のみ」「返信は必ず全員返信」「スケジュールの正はカレンダーのみ」── メール誤送信のような取り返しのつかない事故を防ぐ鉄則を1ファイルに集約し、すべての操作に優先させています。エージェントを「賢くする」より「事故らせない」ほうが、実運用ではずっと重要でした。

特に効いたのが **`skills/`（トリガー発火するワークフロー）** という層です。「常に全手順を読ませる」のではなく「この状況になったらこの手順だけを引き込む」ようにしました。たとえば、

- 「○○社に応募した」→ `new-application` スキルが発火し、登録・ファイル作成・企業研究を一気通貫で実行
- 選考ステータスが変わった → `status-overview-sync` スキルが発火し、**構造化データと俯瞰ビューの両方を必ず同時更新**（片方だけ更新して不整合になるのを防ぐ）
- 「下書き作って」→ `email-draft` スキルが発火し、鉄則に沿った下書きだけを生成

モデルの賢さに丸投げするのではなく、**「いつ・何を・どの手順で」をハーネス側で構造化して与える**。これでメインの定義は読みやすく保たれ、状況ごとの振る舞いが安定しました。

## 第3部 何が変わったか・再現方法

### 何が変わったか

定量化はできませんが、体感で最も大きかったのは **認知負荷が下がった** ことです。

- メールの取りこぼし不安が消えた（10分ごとに見て、タスク化・下書きまでしてある）
- 「今どういう状況か」をいつでも一覧で確認できる（頭の中で覚えなくてよい）
- 面談の振り返りが資産として積み上がる（手応えが消えない）
- 事務処理が裏で回るので、**面接と意思決定という本質に集中できた**

結果として、納得して転職先を決めるところまで走り切れました。エージェントが内定を取ってくれたわけではありません。ただ、**「自分が本当に向き合うべきこと」に時間とエネルギーを残してくれた** ことは、結果に効いたと思っています。

### 自分用に再現するなら

フルセットはやや重いので、効果の大きい順におすすめします。

1. **応募管理を1つのファイル群にする** ── まずは Markdown + frontmatter で「全応募の状態が1箇所でわかる」状態を作る。ここだけでも頭がかなり軽くなる。
2. **絶対NG を明文化する** ── メール・発言・スケジュールの「やってはいけない」を1ファイルに書き、AI に常時読ませる。事故防止の費用対効果が最も高い。
3. **状況別のワークフローを外出しする** ── 「この状況ならこの手順」をスキルとして分離する。
4. **メール監視を常駐させる** ── ここまで来ると「裏で動く相棒」になる。リトライと多重起動防止だけは丁寧に。
5. **面談の文字起こしを自動要約する** ── 振り返りが資産になる。

### 注意点：個人情報の扱い

このシステムは経歴・年収・企業とのやり取りという **極めてセンシティブな情報** を扱います。設計上は、

- 公開してよいもの（応募管理 MCP のような汎用ロジック）と、ローカルに留めるべきもの（経歴・応募データ・メール下書き）を **`.gitignore` で明確に分離**
- 個人データのディレクトリはリポジトリに含めない

としています。ただし `.gitignore` を壊したり強制追加すれば情報は漏れます。**自分専用ツールであっても、機密情報の置き場所と公開境界は最初に設計しておくべき** です。

## おまけ ── 「6月15日」より前でよかった話

このシステムの自動化部分（メール分類・面談要約・定期通知・Discord 応答）は、ほぼすべて `claude -p`（ヘッドレスモード）で動いています。当時はこれが **定額サブスクの範囲内** で回り放題でした。

ところが 2026年6月15日から、Anthropic は `claude -p` や Agent SDK といった **プログラム経由の利用を、サブスクとは別枠の月次クレジット（標準 API レートで消費）に分離** しました。Pro なら月 $20、最上位の Max 20x でも月 $200 ぶんで、超えた分は従量課金です（詳細は [公式ヘルプ](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan) を参照）。

もし転職活動がこの改定の後だったら? 使用実績を集計すると、**記録の残る約1ヶ月分だけで API 換算 $990.51（約15.6万円）**。活動全体ではおよそ **$2,500（約39万円）** に相当します。最上位プランの月次クレジットでも賄えるのは2割ほどで、**月数百ドル単位の実費** を覚悟するか、設計を根本から見直すかの二択になっていたはずです。

「ヘッドレスで安く回すだけだから月数十ドルだろう」という当初の見込みは、実測と20倍以上ずれていました。タイミングに救われた、というのが正直なところです。これから同じものを作る人は、高頻度の定型処理には安いモデル（Haiku など）を振り分けることと、**`/cost` などでの実消費の計測** だけは最初からやっておくことをおすすめします。

## おわりに

転職活動を「ひとりで捌く並行プロジェクト管理」と捉え直し、その事務処理を AI エージェントに常駐で肩代わりさせた ── というのが、このシステムの全体像です。

派手な「AI が転職を自動化する」話ではありません。むしろ逆で、**面接や意思決定という"人間が向き合うべき部分"に集中できるよう、それ以外を徹底的に裏方に回した** 結果でした。

同じように転職活動の事務処理に消耗している人、あるいは自分用の常駐エージェントを作ってみたい人にとって、この設計が何かのヒントになれば嬉しいです。
